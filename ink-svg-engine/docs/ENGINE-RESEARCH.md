# SVG 格斗动画引擎：研究、实现与迁移边界

**研究对象：** `html-playground` 的八人格斗游戏，基线提交 `f38977c5a46a420a9e91695fa74e5ab5e2749038`。  
**实现：** INK 0.1.0，纯 SVG 角色渲染、独立动画核心、工作台、原游戏渲染适配器。  
**结论：** 值得建立专用系统，但引擎应解决“可控、可编辑、可验证”，不能把骨骼插值当成美术品质的自动保证。

## 1. 现有问题到底在哪里

基线并不是没有引擎。`src/atelier-motion.js` 已有动作采样、普通攻击变体、角色特有片段；`game.js` 已有固定步长、输入与格斗判定。继续另起一个名字、再加几种粒子，不会解决人物和动作相似的问题。

从代码看，问题跨了三个层次。

**形体层：** 头身比例、肩部衔接、四肢体积和衣服轮廓不足以支撑大幅动作。把两块有描边的上臂、前臂旋转到正确角度，关节仍可能显出接缝；一张正面脸也不能靠横向缩放自然变成背面。已有衣服、手脚与肢体坐标约定耦合，改比例容易引出遮挡问题。

**动作层：** `select()` 在部分派生没有专属片段时，仍回退到所属角色的已有招式家族。数字上的招式数量，并不等于独立的表演设计。新动作即使增加很多关键帧，若发力方向、重心路线与收势相同，仍会显得一样。

**生产流程层：** 没有便捷的“暂停—拖控制点—改一帧—导出—复测”循环，就会持续依赖改长函数、刷新游戏、凭印象判断。代码复杂度增大，却不一定提升动作质量。

因此，这次的目标不是重写全部格斗规则，而是把动画生产链从原战斗函数中拆出来，并给它可运行的编辑与检查工具。

## 2. 选择混合动画，不选择纯旋转纸偶

我采用了三个互补手段，而不是让所有问题都交给 IK。

### 2.1 骨骼与 IK 决定结构

通用 `Skeleton` 表示父子层级、局部变换、绑定矩阵和世界矩阵。骨盆带动胸腹，肩部再给四肢提供起点。两段 IK 根据手腕、脚踝目标解出肘和膝位置，约束骨长，并显式指定弯曲方向。

参考依据：Spine 官方文档同样把 IK 描述为从目标位置反求一条骨骼链的变换；它与作者直接控制骨骼的方式互补，而不是替代所有姿势设计。[1]

实现中特别处理了目标与根点重合、目标不可达、输入非有限数的情况。对战适配过程中，确实遇到了原骨骼在极端姿势返回零长链的问题；新渲染器对这种退化只修复绘制，不修改原来的战斗几何。

### 2.2 SVG 路径变形决定轮廓

身体不是骨架的可见替身。本版用连续、变宽的曲线包住整条肢体，再把跟随骨段的高光、衣料细节裁在轮廓内，减少“两个圆柱接起来”的接缝。胸腹衣服使用三个骨骼影响区域，按控制点权重变形。

控制点的基本关系为：

```text
变形后的点 = Σ 权重_i × 当前世界矩阵_i × 绑定矩阵_i的逆 × 原始控制点
```

权重非负并且总和为一。Spine 的官方权重资料说明了同一顶点可受多个骨骼影响的思路；这里借鉴的是该思路，但实现对象是 SVG Bézier 控制点，不是 Spine 的贴图网格，也没有使用其运行时。[2]

SVG 路径能否平滑变形还受路径结构限制：W3C 规范要求参与插值的路径具有相同数量、类型和顺序的命令。[3] 因此 INK 先把支持的命令规范化，再维持固定的控制点结构；不会在运行时任意找两张不同 SVG 强行混合。

这也解释了为什么“自动把任何 SVG 导进来就变成高品质角色”不应成为当前承诺。不同拓扑、孔洞、遮挡、轮廓转折需要明确的作者决策。本版拒绝直接绑定 `A/a` 椭圆弧，要求先转成支持的曲线。

### 2.3 替换视图与关键姿势负责不能平滑解决的部分

脸的前视、侧视、背视，张手与握拳，不必全部通过同一个轮廓扭过去。它们可以是同一挂点上的不同附件。骨骼层级也不应强迫视觉遮挡顺序：同一只手有时在脸前，有时在胸后。Spine 的 slot 设计正是将附件及绘制顺序从骨骼层级中分离。[4]

本版已经实现脸部视图、表情、手型和前后图层切换；但没有宣称八个人所有角度都已有独立的手绘替换图。`MorphPath` 支持同拓扑的修形插值，也有测试，当前角色仍缺少成体系的肘、肩、髋和极端俯视修形素材。

春丽的旋转动作暴露了一个典型问题：屏幕上两脚左右交换时，仅插值目标位置会把直腿折成抱膝。本版增加了作者指定的侧向投影缩短关键姿势，缩短的是屏幕投影骨段，绑定骨长不变。这是有限的 2.5D 表现手段，不是真正的三维摄像机和自遮挡求解。

## 3. 让招式通过动作本身区分

工作台包含 27 条独立动作研究。前三个动作家族用于验证同一种骨架能否表达不同动力学特征，而不是追求招式目录长度。

| 角色 | 本次工作台覆盖 | 主要检查点 |
|---|---|---|
| 隆 | 波动拳、升龙拳、龙卷旋风脚 | 双掌送出、紧凑上冲、水平腿旋转是否分开 |
| 肯 | 龙尾脚、升龙拳、迅雷脚 | 前进过顶踢、肩胯换向、分段追击 |
| 春丽 | 百裂脚、旋转鹤脚蹴、天升脚 | 多次收膝、倒立与侧向投影、左右脚交替 |
| 嘉米 | 螺旋箭、加农钉、加农打击 | 低平轴线、上踢翻转、脚先行斜下刺 |
| 卢克 | 沙尘爆破、闪光拳、上升拳动作 | 单拳发射、蓄力保持、拳击式压膝与反冲 |
| 蛛俐 | 岁破冲、五黄杀、天穿轮 | 擦地脚刃、偏轴抬腿、腾空轮转 |
| 不知火舞 | 花蝶扇、飞翔龙炎阵、必杀忍蜂、龙炎舞、鼯鼠之舞、阳炎之舞 | 送扇、翻踢、露肘冲撞、地转、身体俯冲、周身起势分别编排 |
| 八神庵 | 暗拂、葵花、鬼烧 | 低身甩地、分段爪切、上升紫焰；明确为同人客串 |

动作轨道区分预备、发力、跟进与恢复；可使用保持、快速释放、缓入和 Bézier 曲线。并非每两帧都应该使用相同平滑曲线。卢克的蓄势需要可读的停留，春丽的连踢需要多次折膝，俯冲则需要清楚的入射方向。这些是本项目的编排判断，不是对官方动作逐帧复刻的声明。

**27 条研究不等于原游戏 522 个条目均已重新编排。** 对战仍沿用原时间轴。现有派生需要在编辑流程建立后逐条迁移，不能靠修改招式名称或用一条通用曲线自动完成。

## 4. 不知火舞：动作语义与内部名称分离

卡普空在 2025 年 1 月发布的说明明确区分：龙炎舞是地面旋转扫炎；必杀忍蜂是前方侧翻后以肘突进；飞翔龙炎阵是带火焰的空翻膝踢；鼯鼠之舞从空中斜下方向以身体进攻。阳炎之舞还涉及五次焰库存。[7]

本次据此检查动作家族，没有把“飞翔龙炎阵”再画成拿扇子打上勾拳，也没有把“鼯鼠之舞”做成嘉米式伸腿俯踢。

工作台使用可读的标准化名称，而不是继续沿用仓库里容易混淆的内部别名：

| 工作台 ID | 显示名称 | 仓库兼容别名（仅用于迁移索引） |
|---|---|---|
| `mai:hishou-ryuuenjin` | 飞翔龙炎阵 | `ryuenbu` |
| `mai:ryuuenbu` | 龙炎舞 | `hissatsu` |
| `mai:hissatsu-shinobi-bachi` | 必杀忍蜂 | `shinobibachi` |
| `mai:musasabi-no-mai` | 鼯鼠之舞 | `musabi` |
| `mai:kachousen` | 花蝶扇 | `kachosen` |
| `mai:kagerou-no-mai` | 阳炎之舞 | `SA1` |

映射写在每条动作的 `meta.legacyMoveBase`，参考出处写在 `meta.reference`。本版没有偷偷重命名线上游戏数据。上述资料用于核对动作性质，不代表已核对 2026 年所有平衡补丁、每个输入变体或每一帧判定。

## 5. 格斗时间必须和浏览器绘制分离

`requestAnimationFrame` 随显示刷新调度，后台标签页通常会暂停。因此不能把“浏览器又画了一帧”当成“格斗时间必然前进一帧”。[5] 固定时间步与渲染插值的分离，也是固定步长方法的核心；还需要限制追赶步数，避免长期落后时无限补算。[6]

本版的工作台和核心采用以下顺序：

```text
固定模拟步 → Player 进入整数帧 → 发出该帧事件
                         ↓
                    当前动作状态
                         ↓
渲染回调 → 小数帧采样 → FK / IK → 路径轮廓 / 附件 → SVG 属性更新
```

实际战斗的职责边界则是：

```text
输入 / 取消规则 → 战斗状态与招式帧 → 判定 / 命中 / 伤害 / 资源
                         ↓ 只读
                    原姿势和骨骼
                         ↓
                    INK 渲染适配器
```

`seek()` 不派发事件，因此拖时间轴不会重复造成命中。工作台的命中标记只负责预览停顿，不计算伤害。检查中修正了事件与定格姿势相差一帧的问题，增加了“每条动作的 contact 事件必须对应同一姿势帧”的测试。

`Player` 能保存并恢复播放状态，但这不构成完整回滚联机。输入历史、游戏随机数、攻击唯一编号、投技双方约束、弹体、镜头和音效去重都属于另一个更大的状态范围，本轮没有实现它们的完整回滚协议。

本版也尚未把世界空间脚底锁定、成对投技约束、动画事件命中盒编辑器做到生产级。脚踝目标能受 IK 约束，但在带根位移的所有场景中不会自动成为物理地面约束。

## 6. 性能策略与本轮实际证据

初始化和首次绘制完成后复用 SVG 节点，不按帧重建整个角色。路径规范化、绑定逆矩阵和素材分配在初始化完成；绘制只更新变化的属性。胸腹没有局部扭转时走刚体变换快路径，避免无意义地重写每个衣服控制点。

同时要避免一种错误的优化宣传：`performance.now()` 包住 JavaScript 函数测到的时间，不包含浏览器之后的 SVG 栅格化、合成与屏幕呈现。本轮报告里的 CPU 数字只能比较同一测试环境下的同步更新成本，不能据此宣布手机必定 60 FPS 或高刷设备必定 120 FPS。

可复测证据包括：数值与路径验证、随机访问采样、事件与冻结、所有研究动作逐段绘制、动作和形体 JSON 往返导入、真实鼠标控制点编辑、旧/新渲染切换、原有 39 项机制用例和 522 个招式条目回放。完整数字由测试报告生成，见 `TEST-RESULTS.md`。

这些检查能证明“已执行且没有这些已知错误”，不能自动证明人物漂亮、招式忠实官方，或所有潜在游戏 bug 已排除。27 条动作的数值差异检查也不等于感知层面的风格验收，所以还输出无特效的关键姿势对照图。

## 7. 迁移建议：先固化资产标准，再扩大招式覆盖

我不建议直接把 27 条工作台动作全部映射上线，然后让玩家替我们发现手脚与判定不一致。合理的下一步是选择一个角色的三条代表动作，完成“美术—时序—挂点—判定”的闭环，再扩展到剩余角色。

**第一道门槛是形体。** 为每个角色建立自己的前/侧/后头部、手型、肩肘与服装遮挡图，确定身高、肩宽、肢体体积与描边标准。工作台的比例滑块不是这一步的替代品。当前脸部仍有共用结构，衣服大量继承旧 SVG，极端角度还需要手绘。

**第二道门槛是动作。** 每招至少审阅预备、接触、跟进和收势四个关键姿势；检查不加火焰或残影时是否仍能辨认。先改轮廓与节奏，再增加特效。曲线和 IK 是实现手段，不应反过来限制作者只能画几个万能姿势。

**第三道门槛是战斗接入。** 将新 Clip 的三个阶段显式映射到原招式时序，并逐个对齐有效挂点、击中位置、位移与取消切换。原游戏负责的跳跃与突进，不能再叠加一次编辑器根位移；视觉投影缩短也不应偷偷缩小权威碰撞盒。

**第四道门槛是设备与内容验收。** 在真实手机、目标浏览器、背景特效最重的场景下测绘制开销；检查左右朝向、空中、墙角、投技、命中停顿和招式取消。再决定是否替换主页面，而不是依据一张好看的截图判断整个角色库合格。

## 8. 本次交付意味着什么

已得到一个真实可运行的生产工具雏形：可以独立编辑姿势与形体，保存可移植数据，查出事件和绘制错误，并在原游戏中对照新的身体轮廓。原 `main` 没有被本轮修改，原战斗文件也不被构建脚本覆盖。

尚未得到“把所有旧素材变完美”的自动机器，也没有完成全部招式逐一的官方动作标定。系统已经让后续高质量美术与动作制作有落脚点；最终质量仍取决于逐角色的素材和逐招的编排是否真正完成。
